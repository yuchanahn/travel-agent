# 011 — 한 응답의 웹 도구 요청을 병렬로 실행하기

2026-10-17 · 구현과 실제 로컬 모델 실험

## 문제 정의와 좋은 답변의 기준

사용자는 여행 요청을 본격적으로 실험하기 전에, 독립적인 여러 검색을 모델이 한 번에 요청하고 실행기도 동시에 처리하기를 원했다. 기존 실행기는 여러 tool_calls를 받을 수 있었지만 하나씩 기다렸다. 서로 다른 장소의 공식 주소를 찾는 검색은 앞 검색의 결과를 기다릴 필요가 없다.

이번 검증은 두 층으로 나눴다. 실행의 기준은 모델이 실제 도구 두 개를 같은 응답으로 요청하고, 실행 구간이 겹치며, 각각의 결과가 원래 요청에 맞춰 다음 모델 호출에 전달되는 것이다. 답변의 기준은 반환된 공식 주소 두 개와 출처를 알려주거나, 실패한 검색을 확인 불가로 구분하는 것이다. 병렬 실행 성공이 답변 품질 성공을 뜻하지 않는다.

## 먼저 같은 질문을 순차 실행으로 보냈다

서로 독립적인 두 공식 홈페이지 검색을 한 묶음으로 요청했다. 가상의 개인 일정이나 비밀정보는 넣지 않았다. 두 검색 모두 top_k=1을 요청해 검색 개수와 문맥을 제한했다. 이 개발 질문은 병렬 호출 능력을 명시적으로 유도하며 자연스러운 최종 여행 요청에 대한 자율 계획 평가는 아니다.

> **질문**
> 춘천 삼악산 호수케이블카와 국립춘천박물관의 공식 홈페이지 주소를 각각 찾아줘. 서로 독립적인 두 웹검색을 한 응답의 도구 요청 묶음으로 보내고, 각 검색은 top_k=1로 해줘. 반환된 주소와 출처를 간결하게 알려줘. 본문을 읽었다고 말하지 마.

```text
춘천 삼악산 호수케이블카 공식 홈페이지는 [https://samaksancablecar.com/](https://samaksancablecar.com/) 입니다. ([web:42a1dc11003496ff])

국립춘천박물관 공식 홈페이지 검색 결과가 없었습니다.
```

Qwen은 실제로 한 응답의 tool_calls에 검색 두 개를 넣었다. 순차 모드에서는 첫 검색이 끝난 뒤 두 번째가 시작됐다. 케이블카 주소는 실제 반환된 결과에 근거했지만 박물관 검색은 제공자 오류였다. 모델은 이를 “검색 결과가 없었습니다”로 표현했다. 제공자가 정상 검색으로 빈 목록을 반환한 것과는 다르므로 이 설명은 충분히 정확하지 않다.

## 문제 분석과 구현 선택

모델의 한 응답은 하나의 메시지지만 여러 도구 요청을 담을 수 있다. 병렬화할 부분은 LLM 호출을 여러 개 만드는 것이 아니라 그 메시지를 받은 실행기의 도구 처리다. 결과를 모두 수집한 뒤 다음 LLM 호출로 넘긴다. 앞선 결과를 보고 결정해야 하는 검색은 다음 턴에서 요청해야 한다.

네트워크 I/O인 web_search에는 표준 라이브러리 ThreadPoolExecutor를 사용했다. 기본 worker 수는3, 허용 범위는1..4다. 1이면 비교용으로 모든 도구를 요청 순서대로 실행한다. 메모리 조회는 SQLite 연결과 로컬 검색 모델을 공유하므로 호출 스레드에서 실행한다. 웹 작업은 먼저 제출하므로 메모리 조회와 겹칠 수 있지만 여러 메모리 조회끼리는 병렬화하지 않았다.

실행 전 전체 묶음의 호출 한도·프로토콜과 개별 인자를 검사한다. 같은 검색은 스레드를 시작하기 전에 예약·중복 검사해 한 묶음 안의 중복도 막는다. 각 실행은 실제 시작 직전 남은 시간을 다시 검사한다. 실패는 해당 호출의 결과로 남기고 다른 성공 결과를 버리지 않는다.

완료 순서와 모델에 전달하는 순서는 분리했다. 결과는 원래 요청 인덱스에 저장하고 tool_call_id를 유지해 순서대로 메시지에 추가한다. 호출별 trace는 실제 시작·종료 시점에 남기며 Lock으로 sequence와 한 줄 쓰기를 보호한다.

## 병렬 실행으로 바꾼 뒤 같은 질문

> **질문**
> 춘천 삼악산 호수케이블카와 국립춘천박물관의 공식 홈페이지 주소를 각각 찾아줘. 서로 독립적인 두 웹검색을 한 응답의 도구 요청 묶음으로 보내고, 각 검색은 top_k=1로 해줘. 반환된 주소와 출처를 간결하게 알려줘. 본문을 읽었다고 말하지 마.

```text
죄송합니다. 현재 웹 검색을 통해 공식 홈페이지를 찾을 수 없었습니다.

*   **춘천 삼악산 호수케이블카**: 공식 홈페이지가 확인되지 않았습니다.
*   **국립춘천박물관**: 공식 홈페이지가 확인되지 않았습니다.

다른 검색어로 시도하거나, 과거에 기록된 정보를 찾아보시는 것이 좋을 것 같습니다.
```

모델은 이번에도 도구 두 개를 한 번에 요청했다. 두 실행 구간은 겹쳤고, 두 오류를 받은 뒤 최종 답변을 냈다. 그러나 이번에는 외부 제공자가 두 검색 모두 `No results found` 오류를 반환해 주소를 받지 못했다. 실행 병렬화는 확인됐지만 두 공식 주소를 안내한다는 답변 기준은 통과하지 못했다.

실행 구간은 요청 시작 이후의 초 단위 상대 시각이다.

| 실행 | 검색1 시작~종료 | 검색2 시작~종료 | 관찰 |
|---|---|---|---|
| workers=1 | 6.037~7.265 | 7.265~7.644 | 겹치지 않음, 한 검색 성공·한 검색 오류 |
| workers=3 | 1.047~1.377 | 1.047~1.370 | 겹침, 두 검색 오류 |

기본 엔진 조합의 일시적인 문제인지 확인하려고 같은 질문을 brave,google 조합으로 한 번 더 실행했다. 설정은 그 프로세스에만 적용했고 기본값은 바꾸지 않았다.

> **질문**
> 춘천 삼악산 호수케이블카와 국립춘천박물관의 공식 홈페이지 주소를 각각 찾아줘. 서로 독립적인 두 웹검색을 한 응답의 도구 요청 묶음으로 보내고, 각 검색은 top_k=1로 해줘. 반환된 주소와 출처를 간결하게 알려줘. 본문을 읽었다고 말하지 마.

```text
*   **춘천 삼악산 호수케이블카**: 공식 홈페이지가 확인되지 않았습니다.

```

대체 엔진 조합도 두 검색 모두 같은 제공자 오류를 반환했다. 원인이 차단인지·질의 문제인지·공급자의 결과 추출 문제인지는 확인하지 못했다. 이번 결과만으로 병렬화가 검색 실패를 일으켰다고 결론 내릴 수도 없다. 순차 실행에서도 실패가 있었다.

## 결과와 남은 한계

43개 단위 테스트가 통과했다. 추가6개는 동기화 장치로 두 실행이 겹치는지, 완료 순서가 바뀌고 한 호출이 실패해도 결과와 ID가 맞는지, 동시 실행 수 제한, 메모리의 소유 스레드 유지, 중복·비활성화 차단, 기한이 지난 작업의 미실행을 검사한다. 이 테스트의 제공자 결과는 합성이다. 실제 웹검색 결과를 얻었다고 취급하지 않는다.

실제 로컬 모델3회 실행에서는 모두 한 응답에 두 web_search를 요청했다. 순차1회는 겹치지 않았고 병렬2회는 시작·종료 구간이 겹쳤다. 병렬2회 모두 제공자 실패여서 실제 성공 결과 두 개를 동시에 수집하는 것은 이번 외부 통합 실험에서 확인하지 못했다. 성공 결과의 취합·실패 격리는 합성 계약 테스트로 확인했다.

독립적인 요청을 묶으면 도구를 하나씩 요청하는 모델 왕복을 줄일 수 있지만, 이번 순차·병렬 비교는 둘 다 이미 한 묶음으로 요청해 모델 호출 수는 동일하게2회였다. 모델 로딩·공급자 결과·실패 조건이 달라 전체 응답 시간 차이를 속도 향상 수치로 해석하지 않는다. 도구 호출 수도2회로 같았다. 병렬화가 검색 개수나 토큰 자체를 줄여주지는 않는다.

이미 시작된 Python 스레드는 강제 종료하지 않는다. 작업을 기다리므로 공급자가 늦어지면 전체 제한을 넘길 수 있다. 동시 검색은 제공자 측 요청 부하를 늘릴 수 있고 서비스 전체 요청 큐·전역 rate limit은 아직 없다. 여러 결과가 입력 예산을 넘으면 기존 context_limit으로 멈춘다. 향후 쓰기·예약 도구는 이 병렬 허용 목록에 자동 포함시키지 않는다.

다음 제품 실험에서는 구체적인 여행 조건을 주고 모델이 스스로 검색을 나누는지, 실패했을 때 적절하게 재검색하거나 유보하는지 확인한다. 이번 실험은 그 전에 필요한 실행기 기능을 검증한 단계다.
