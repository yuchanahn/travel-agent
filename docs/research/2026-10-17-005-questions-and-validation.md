# 005 — 미정인 여행 요청에서 시작하는 구현·검증 계획

날짜: 2026-10-17 (Asia/Seoul). 상태: 질문·기대 행동·검증 계획 정리 완료. 에이전트 구현·평가 실행 전.

## 프로젝트에 접근하는 관점

여자친구가 여행을 가자고 해서 Codex에 여행 계획을 요청했지만, 불필요한 토큰 소비와 기대에 못 미치는 결과라는 불편을 느꼈다. 실제 여행 결정을 돕는 전용 에이전트를 직접 만들고 공개한다.

기술 목록부터 채우지 않고 실제 요청 → 필요한 결정 → 기대 행동 → 실패 기준 → 데이터·도구 → 최소 구현 → 비교 실험 순서로 접근한다. 코드는 현재 워크스페이스에서 Python으로 개발하고 GitHub에 변경을 기록한다. Ollama는 모델 공급을 담당하고, Python 애플리케이션은 대화 상태·도구 실행·제한·관찰 기록을 담당한다.

사용자의 불편은 프로젝트의 출발점이다. 전용 에이전트가 Codex보다 비용이 적거나 결과가 좋다는 것은 아직 검증하지 않았다.

## 첫 번째 대표 요청

> 여자친구랑 여행 가고 싶은데 아직 정한 게 없어. 어디부터 정하면 좋을지 도와줘.

출발지·날짜·여행 기간·예산·차량 유무·취향은 미정으로 둔다. “여자친구와 여행”이라는 맥락은 있지만 정확한 인원은 추가 동행이 언급될 때 확인한다. 서울 출발·40만 원·차량 없음 같은 과거 테스트 조건을 이번 사용자 조건으로 가져오지 않는다.

국내 1박 2일은 기존에 논의한 첫 제품 범위의 제안이다. 실제 사용자의 확정 조건으로 취급하지 않는다. 해외나 장기 여행 요청은 초기 지원 범위를 설명하고 대안을 제시할 수 있다.

## 이 요청에서 기대하는 첫 행동

완성된 일정표를 곧바로 만들어내기보다, 선택을 좁히는 데 중요한 조건부터 간단히 확인한다.

- 가능한 질문: “출발 지역과 대략 며칠 정도 다녀올 수 있는지 알려줄래요? 아직 미정이면 가까운 짧은 여행부터 같이 비교해볼게요.”
- 출발지를 정할 수 없다면 특정 도시를 사실처럼 가정하지 않는다.
- 날짜가 미정이라면 확정 날짜 대신 주말·평일, 계절, 가능한 기간처럼 답하기 쉬운 선택지를 제시한다.
- 예산이 미정이면 총액인지 1인당인지 구분할 수 있는 범위를 안내한다.
- 사용자가 계속 “미정”이라고 하면 같은 질문만 반복하지 않고 여행 유형과 선택 기준을 보여준다. 예시를 위한 가정은 표시한다.
- 첫 질문의 개수나 문구를 정답으로 고정하지 않는다. 우선순위가 낮은 조건까지 한꺼번에 설문처럼 요구하지 않는지 평가한다.
- 날짜·노선별 가격 검색 등 아직 의미가 없는 조회를 무작정 실행하지 않는다.

## 사용자가 결정을 내릴 수 있는 결과

조건이 충분해지면 후보를 비교한다. 후보 수는 우선 2~3개를 기준으로 하되, 근거가 부족하면 수를 억지로 채우지 않는다.

- 후보가 조건에 맞는 이유
- 이동 방법과 이동 부담
- 예상 비용의 포함 항목·기준 인원·조회 시점·미확인 항목
- 즐길 거리와 취향상 장단점
- 조건별 비교와 추천 이유
- 출처, 조회 사실과 추정의 구분
- 다음으로 사용자가 선택하거나 확인할 것

조건이 충분하지 않으면 유용한 추가 질문이나 탐색용 비교를 제시한 것도 정상 종료다. 매번 최종 여행지를 확정하는 것을 성공으로 삼지 않는다. 예약·결제는 첫 범위에서 제외한다.

## 대표 질문과 검증 사례

아래 숫자·지역은 평가용 가상 조건이다. 실제 커플의 여행 조건과 구분한다.

### Q01 — 전부 미정

입력: “여자친구랑 여행 가고 싶은데 아직 정한 게 없어. 어디부터 정하면 좋을지 도와줘.”

확인: 중요한 조건을 우선 확인하고 출발지·기간·예산을 지어내지 않는다. 이유 없는 실시간 가격 조회를 시작하지 않는다.

### Q02 — 미정을 반복하는 사용자

대화: Q01 후 “출발지 말고는 다 미정이야. 서울에서 출발해. 네가 선택지를 좀 줘.”

확인: 서울을 기억하며, 미정인 조건을 확정하지 않는다. 같은 질문을 반복하는 대신 짧은 근교 여행·숙박 여행 등 탐색 가능한 유형과 장단점을 제시한다.

### Q03 — 예산 의미가 불분명

입력: “둘이 30만 원 정도로 다녀오고 싶어.”

확인: 총예산인지 1인당인지 임의로 확정하지 않는다. 장소·기간 등 필요한 정보와 함께 자연스럽게 확인한다.

### Q04 — 명시된 조건 유지

입력: “서울 출발, 차 없이 둘이 총 40만 원으로 1박 2일. 여행지 후보를 비교해줘.”

확인: 자동차 필수 코스를 추천하지 않는다. 비용은 두 사람·전체 여행 기준으로 구분하고, 근거 없이 예산 충족을 보장하지 않는다.

### Q05 — 날짜 미정과 실시간 가격

입력: “날짜는 미정인데 숙소랑 교통비를 지금 확정해서 알려줘.”

확인: 확정 견적의 한계를 설명하고 날짜 범위 확인이나 추정 범위를 제안한다. 확인하지 않은 가격을 현재 확정 가격처럼 말하지 않는다.

### Q06 — 조건 변경

대화: Q04 후 “예산은 총 25만 원으로 바꿀게. 차는 여전히 없어.”

확인: 새 예산을 반영하고 차량 없음은 유지한다. 이전 후보가 조건에 맞지 않으면 재검토하며 이전 금액을 계속 쓰지 않는다.

### Q07 — 조회 실패 또는 결과 없음

입력: Q04. 도구 조건: 검색 타임아웃 또는 빈 결과를 반환한다.

확인: 검색 성공을 꾸미지 않는다. 오류 유형에 맞게 제한된 재시도·대안·조건 조정을 제안하고 무한 반복하지 않는다.

### Q08 — 가상·미검증 정보

입력: Q04. 도구 조건: “테스트용 가상 데이터, 가격 미검증”이라고 표시한 여행 결과를 반환한다.

확인: 실제 검증 가격으로 제시하지 않는다. fixture 표시와 불확실성을 최종 답변에서도 유지한다. 기존 로컬 실험에서 발견한 실패의 회귀 사례다.

### Q09 — 조건 충돌

입력: “둘이 총 5만 원으로 이동비랑 숙박비까지 포함해서 1박 2일 가고 싶어.”

확인: 조회 근거 없이 가능·불가능을 단정하지 않는다. 비용 범위와 조건을 확인하고 어려울 때 당일치기 등 조정안을 제시한다.

### Q10 — 필요 없는 질문·조회 줄이기

입력: 출발지·기간·예산·차량·취향을 이미 제공한 요청.

확인: 이미 받은 정보를 다시 묻지 않고 필요한 조회로 진행한다. 같은 인자의 조회를 이유 없이 반복하지 않는다.

## 평가 방법 — 첫 버전

첫 단계는 수동 판정이다. 각 사례마다 기대 행동을 미리 고정한 뒤 결과를 확인한다. “좋은 여행지” 하나를 정답으로 강제하지 않는다.

- 조건 준수: 명시된 제약과 변경된 조건을 지켰는가?
- 질문의 필요성: 추천을 바꿀 중요한 정보를 확인했는가? 반복·불필요한 질문을 피했는가?
- 근거와 불확실성: 조회 사실·추정·미확인·가상 데이터를 구분했는가?
- 도구 사용: 필요한 도구와 올바른 인자를 선택하고 실제 결과를 반영했는가?
- 실패와 종료: 조회 실패를 알리고 정해진 횟수·시간 예산 안에서 종료했는가?
- 사용자 효용: 선택지를 좁히거나 다음 결정을 하는 데 도움이 되었는가?

항목별 통과·실패·해당 없음과 판단 근거를 기록한다. 적용 항목의 통과 수/전체 수를 보고하고, 사용자 효용은 사용자 선호와 이유를 별도로 기록한다. 허위 조회·미확인 가격 확정·명시 제약 위반은 따로 집계하여 평균 점수에 가리지 않는다.

질문 수·도구 호출 수·토큰 수는 관찰 지표다. 무조건 적을수록 좋다고 판단하지 않는다. 입력·출력 토큰, 전체 지연, 로딩 지연, 도구 호출, 오류, 종료 이유를 함께 기록한다. 로컬 호출 토큰을 API 요금으로 환산한 절감액이나 전력비로 간주하지 않는다.

Q07~Q08은 고정된 테스트 도구로 재현한다. 실제 여행 데이터 평가는 별도로 출처·조회 시점·응답 스냅샷을 남긴다. 사례 10개와 한 번의 실행은 탐색용이며 안정적인 일반 성공률을 주장하지 않는다.

## 구현에 접근하는 순서

1. 지금 정리한 대표 요청과 기대 행동을 기준선으로 삼는다.
2. 실제 조회 없이 대화 상태와 미정 조건 처리를 먼저 구현한다. 추가 질문·탐색용 제안이 가능한지 확인한다.
3. Ollama 어댑터와 단일 도구 호출 루프를 구현한다. 도구 allowlist·인자 검증·호출 및 시간 제한·오류 결과를 포함한다.
4. 고정된 테스트 도구로 호출 왕복과 실패 처리를 검증한다. 가상 결과를 실제 검색처럼 소개하지 않는다.
5. 여행 데이터의 출처·이용 조건·갱신 시점을 조사하고 첫 실제 조회 도구 하나를 연결한다.
6. Q01~Q10을 실행해 실패를 기록하고 반복되는 문제 하나씩 수정한다.
7. 같은 모델의 직접 답변과 도구 기반 에이전트를 비교한다. 조회 정보 접근 차이도 결과에 영향을 준다고 명시한다. 설계 자체를 비교하려면 동일한 검색 결과를 주는 통제 실험을 추가한다.
8. 사용자 화면과 배포를 붙이고 실제 사용자의 선택·불편·재사용을 확인한다. 범용 Codex와 비교할 때는 모델·도구·조건 차이를 기록한다.

이번 작업에서는 질문과 검증 설계만 정리했다. 실제 대화 상태·에이전트 루프·여행 검색·평가 실행은 아직 하지 않았다.

## 다음 구현의 완료 기준

대표 요청 Q01을 입력하고, 에이전트가 필요한 조건을 묻고, 사용자의 Q02 응답을 기억하며, 미정인 조건을 지어내지 않고 다음 선택을 돕는 첫 대화 흐름을 로컬 CLI에서 확인한다. 실제 검색 도구가 없는 상태를 명시한다.

## 연구 기록

매 작업에서 문제·가설·변경·실행 조건·관찰·실패·결정·다음 실험을 남긴다. 노션에는 이 문서와 동일한 계획을 기록하고, 저장소에는 재현 가능한 변경과 결과를 남긴다. 공개용 대화는 합성·익명화된 사례만 사용한다.
