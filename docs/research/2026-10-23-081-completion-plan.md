# 공고 요구사항별 마무리 계획 — 081

사용자는 RAG의 기존 설명 근거를 활용하고, 공고의 각 요구사항에 답하는 형태로 Notion을 구성하며, 작은 테스트·모니터링 검증·제품 흐름의 구체적인 계획을 요청했다. 사용자에게 기간과 비용·모델 선택을 먼저 물었고,3~5일·현재 로컬 Qwen/Python 유지·추가 비용 없음으로 답했다.

## 확인한 기존 근거

007에는 BM25/Dense/Hybrid의4문항 Hit@3·MRR 비교와 요약 손실 뒤 원문 검색으로 이유를 복원한 실제 답변이 이미 있었다.057에서는 웹 요약·BM25·원문 연결을 확인했지만 계단87개 복원 뒤 근거 없는 관계 해석이 남았다.079는 여행2질문을 종료했으나 근거 품질0/2다. 기존 웹에도 호출/token·도구 로그가 있으므로 모니터링을 신규 도입한 것으로 포장하지 않는다.

## 계획과 문서 구성

[구체적인 실행 환경·순서·문항 수·통과 기준·중단선](../portfolio/completion-plan.md)을 정리했다. 하네스·RAG·평가/관측·제품 흐름 상세4개를 포트폴리오 아래에 만들고 상위 구현 과정에서 연결했다. RAG 항목은 실제 질문·답변과 기존 검색 성적을 포함하며 합성 소표본·실행 시점·웹/CLI 범위를 밝힌다. 코드 조각과 구조도는 기존 구현에서 가져왔고 계획상 기능은 구현 전으로 표시했다.

새 쉬운 기능 평가로 기존 여행 실패를 덮지 않는다. 먼저 기대 근거와 기준을 정하고, 실패한 실제 사례만 같은 조건의 개선과 연결한다. 이미 정상인 기능은 기능 확인으로 설명한다. 최대3~5일 뒤에는 결과가 부족해도 시간을 계속 늘리지 않고 한계를 남긴다.
