### 1. 문제 정의 — 요청과 초기 결과

멘토가 제안한 BM25·하이브리드·리랭킹을 이해하고 현재 장비에서 비교할 구현안을 정하는 단계였다. 초기 답변·개선 답변을 생성한 단계는 아니며, 당시 RAG 벤치마크 stdout은 없다.

### 2. 문제 분석

BM25 점수와 벡터 유사도의 척도가 다르고, 검색·순위 결합·리랭킹의 역할도 다르다. 관광 문서를 넣자는 초기 제안은 이후 사용자와의 논의로 대화 원문 메모리로 변경됐다. 초기 제안을 현재 채택안으로 덮어쓰지 않는다.

### 3. 연구 과정

### 4. 문제 해결

설계는007에서 구현·실험으로 이어졌다. 다음은 그때 구현된 실제 RRF 함수다. 006 당시 이미 실행했다는 뜻이 아니다.

출처: `src/travel_agent/memory.py`. 종류: **후속 구현의 실제 코드**. 원본 파일 SHA-256: `c9b3c0f3c9679077c651b908835822205f8fd1dccdedca610bcfceb723a5b631`. 발췌 내용은 고치지 않았다.

```python
def rrf(rankings: list[list[int]], k=60) -> dict[int, float]:
    scores: dict[int, float] = {}
    for ranking in rankings:
        for rank, index in enumerate(ranking, 1):
            scores[index] = scores.get(index, 0.0) + 1 / (k + rank)
    return scores
```

## 3. 논문과 구현 자료에서 얻은 판단

### 3.1 RAG를 “벡터 DB 도입”과 동일시하지 않는다

Lewis 등의 원 RAG 논문은 생성 모델과 외부 검색 메모리를 결합한다. 원 논문의 dense Wikipedia index와 학습 방식을 그대로 재현하는 프로젝트는 아니다. 여기서는 고정된 여행 코퍼스의 검색 결과를 기존 Ollama 생성 모델에 제공하는 응용 RAG를 만든다. 검색과 생성은 따로 평가한다.

근거: [Lewis et al., Retrieval-Augmented Generation for Knowledge-Intensive NLP Tasks, 2020](https://arxiv.org/abs/2005.11401).

### 3.2 BM25는 별도 리랭커가 아니라 1차 검색의 기준선이다

BM25는 단어 빈도, 문서 빈도와 길이 정규화 등을 이용해 쿼리와 문서의 관련성 점수를 계산한다. 점수로 순위를 만들므로 “랭킹”이 맞지만, 임베딩 검색 후 별도 모델이 후보를 다시 읽는 리랭킹과는 구분한다.

여행에서는 지명·역명·시설명처럼 정확한 명칭이 중요한 경우를 BM25로 확인한다. 반면 “조용히 쉬고 싶다”와 문서의 “한적한 산책” 같은 표현 차이는 dense 검색의 가치를 확인할 사례다. 이 역할 분담은 우리 데이터에 대한 가설이며 두 검색법 중 하나가 특정 유형을 항상 해결한다고 보장하지 않는다.

BEIR 논문은 18개 데이터셋에서 BM25가 강한 기준선임을 보였고, 재순위화 계열의 평균 성능과 계산 비용 사이의 교환관계도 보고했다. 이 결과를 한국어 여행 데이터의 예상 점수로 옮기지 않는다. BM25-only를 비교에서 빼지 않아야 한다는 근거로 사용한다.

근거: [Stanford IR book, Okapi BM25](https://nlp.stanford.edu/IR-book/html/htmledition/okapi-bm25-a-non-binary-model-1.html), [Thakur et al., BEIR, 2021](https://arxiv.org/abs/2104.08663).

### 3.3 Hybrid 통합은 RRF부터 시작한다

BM25 점수와 cosine similarity를 그대로 더하면 서로 다른 점수 척도를 다루게 된다. 첫 구현은 점수 보정이나 학습 가중치를 도입하기보다 순위 기반 Reciprocal Rank Fusion을 사용한다.

문서 d의 점수는 각 검색 목록에 등장한 순위에 대해 1 / (k + rank)를 합산한다. 순위는 1부터 시작하며 미등장 목록은 기여하지 않는다. 초기 k=60, 두 검색의 가중치는 동일하게 둔다. 원 논문에서 사용한 k=60을 재현 가능한 출발값으로 택한 것이며 여행 검색의 최적값으로 주장하지 않는다.

RRF는 검색 목록을 합치는 방법이다. 새 텍스트 이해 모델도 아니고, 별도 cross-encoder 리랭커도 아니다. 원 논문에서도 모든 조건에서 개별 최고 순위를 이긴 것은 아니므로 hybrid의 개선은 실험으로 확인한다.

근거: [Cormack, Clarke & Buettcher, SIGIR 2009 원문](https://cormack.uwaterloo.ca/cormacksigir09-rrf.pdf).

### 3.4 리랭킹은 좁힌 후보에만 적용한다

bi-encoder로 문서를 미리 임베딩하는 것과 달리, cross-encoder는 질문과 후보 문서를 함께 입력해 관련성 점수를 계산한다. 후보마다 계산하므로 전체 코퍼스가 아닌 1차 검색의 상위 후보에 적용한다. 첫 검색에서 빠진 근거는 리랭커가 되찾을 수 없다.

따라서 후보 recall과 최종 순위 품질을 분리해 측정해야 한다. 리랭커 점수나 sigmoid 값은 문서의 사실성·여행 가능성 확률로 취급하지 않는다.

근거: [Sentence Transformers Retrieve & Re-Rank](https://sbert.net/examples/sentence_transformer/applications/retrieve_rerank/README.html), [BAAI bge-reranker-v2-m3 모델 카드](https://huggingface.co/BAAI/bge-reranker-v2-m3).

## 4. 후보 비교와 선택 이유

### 4.1 한국어 lexical 검색: Kiwi + rank_bm25

권고: kiwipiepy로 질문·문서를 같은 방식으로 토큰화하고 rank_bm25의 BM25Okapi로 시작한다.

rank_bm25는 전처리를 대신 하지 않고 문자열 토큰 목록을 받는다. 작은 코퍼스에서 형태소 토큰과 BM25 점수를 직접 관찰하기 쉬워 첫 학습 구현으로 선택한다. 저장 시 원문·청크·토큰화 설정으로 재구성할 수 있게 하고, 임의의 pickle 로딩을 재현 절차로 삼지 않는다.

한국어는 공백 분리만 했을 때 조사·활용·복합 지명에 따른 불일치가 생길 수 있다는 가설을 검증한다. Kiwi가 공식적으로 Windows를 지원한다는 점도 선택 근거다. 다만 명사만 남기면 “차 없이”, “운영하지 않음” 같은 조건이 사라질 수 있어 부정·수치·지명 처리를 검토한다. 질의와 문서에 동일한 정규화 버전을 적용한다.

대안 bm25s는 인덱스 저장과 NumPy 기반 검색을 제공한다. 코퍼스나 조회 지연이 커지면 동일한 청크·질의에서 교체 비교한다. 기본 BM25 변형과 IDF 처리 차이를 고정·기록해야 하며 라이브러리 교체 효과를 토큰화 개선 효과와 섞지 않는다. Elasticsearch/OpenSearch 서버는 지금 규모에서 운영 변수가 추가되므로 첫 단계에서는 보류한다.

근거: [rank_bm25](https://github.com/dorianbrown/rank_bm25), [kiwipiepy](https://github.com/bab2min/kiwipiepy), [bm25s](https://github.com/xhluca/bm25s).

### 4.2 임베딩: multilingual-e5-small을 CPU 기준선으로

권고: intfloat/multilingual-e5-small, Sentence Transformers 또는 Transformers의 공식 사용 방식, CPU 실행으로 시작한다.

모델 카드는 384차원, 512토큰 제한과 비영어에서도 query:/passage: prefix를 요구한다. 정규화한 벡터의 내적으로 cosine 검색을 구성한다. 한국어를 포함한 다국어 후보이며 이 코퍼스에서 성능이 충분한지는 별도 검증한다.

최신 최고 모델이라고 선택하는 것이 아니다. 초기 코퍼스가 작고 질문·문서를 짧게 나눌 계획이라, 작은 모델로 재현 가능한 dense 기준선을 먼저 만들려는 선택이다. 원문을 조용히 512토큰으로 잘라 정보가 사라지지 않도록 입력 길이를 검사한다. 모델 revision·prefix·정규화·토크나이저를 인덱스 메타데이터에 고정한다.

대안 Qwen3-Embedding-0.6B는 공식적으로 32K 문맥·1024차원·다국어·instruction 지원을 제공한다. 비교 가치가 있지만 지금 생성 모델과 계열이 같다는 이유만으로 채택하지 않는다. E5의 한국어 검색 누락이 확인되면 같은 코퍼스·질의에서 품질과 지연을 비교한다. 다국어 벤치마크 평균을 우리 여행 검색의 우열로 간주하지 않는다.

근거: [Multilingual E5 기술 보고서](https://arxiv.org/abs/2402.05672), [E5-small 공식 모델 카드](https://huggingface.co/intfloat/multilingual-e5-small/raw/main/README.md), [Qwen3-Embedding 공식 저장소](https://github.com/QwenLM/Qwen3-Embedding).

### 4.3 벡터 저장·검색: 첫 단계는 NumPy exact search

권고: 정규화된 float32 행렬을 로컬 파일에 저장하고, 청크 메타데이터는 JSONL로 관리한다. 검색 시 전체 벡터와 내적해 정확 검색한다. 별도 벡터 DB 서버는 시작하지 않는다.

첫 코퍼스는 50~100개 문서를 목표로 하되 실제 청크 수는 수집 후 확인한다. 예를 들어 1만 청크 × 384차원 × 4바이트는 벡터 원소만 약 15.36MB이며 모델·메타데이터·검색 임시 메모리는 별도다. 작은 규모에서 ANN 오차와 서버 운영을 추가하기보다 검색 알고리즘 자체를 관찰하려는 설계다.

이는 RAG나 dense 검색을 생략하는 결정이 아니다. 지속 업데이트·필터·동시성·지연이 병목이 되면 FAISS 또는 벡터 DB를 검토한다. 첫 평가에서는 동일한 청크 집합에 BM25와 dense를 적용한다.

### 4.4 별도 리랭커: bge-reranker-v2-m3를 실험 구성에 포함

권고: BAAI/bge-reranker-v2-m3를 Transformers 또는 Sentence Transformers CrossEncoder로 CPU에서 먼저 시험한다. 모델 카드에는 다국어 reranker와 Apache-2.0 라이선스가 명시돼 있다. 한국어 여행 성능이나 CPU 속도는 아직 확인하지 않았다.

장점은 기존 생성 모델의 자유 형식 점수 대신 별도 관련성 모델로 후보 재정렬을 분리해 비교할 수 있다는 점이다. 단점은 CPU 지연과 모델 RAM·다운로드가 추가된다는 점이다. 원문과 질의의 합산 토큰 길이, batch size와 thread 수를 기록한다. CPU에서는 우선 float32로 정확성 기준을 잡고 양자화는 별도 실험으로 분리한다.

Qwen3-Reranker-0.6B도 비교 후보지만 별도 decoder 기반 점수 추출 방식과 instruction 구성이 추가된다. 첫 구현에서는 BGE의 sequence-classification 형태를 선택한다. 이는 성능 우위의 주장이 아니다.

리랭커는 학습 목표상 구현·평가에 포함한다. 다만 서비스 기본 활성화 여부는 hybrid 대비 검색 품질과 지연을 측정한 뒤 정한다. 느리면 후보 수·입력 길이를 줄이는 실험을 하거나 GPU 순차 실행을 검토하고 모델 교체 비용도 측정한다.

근거: [BGE 모델 카드와 Transformers 예제](https://huggingface.co/BAAI/bge-reranker-v2-m3), [FlagEmbedding](https://github.com/FlagOpen/FlagEmbedding), [Qwen3-Embedding/Reranker](https://github.com/QwenLM/Qwen3-Embedding).

## 5. 권고 파이프라인과 초기값

문서 처리:
출처·사용 조건 확인 → 원문과 수집 시점 보존 → 제목·문단 단위 정제 → 청크 생성 → 같은 청크 ID로 BM25 토큰 및 dense 벡터 생성 → 인덱스 manifest 저장.

검색:
질문 → 한국어 토큰 BM25 상위 20개 + E5 dense 상위 20개 → chunk_id 기준 합집합·중복 제거 → RRF → 상위 20개를 리랭킹 → 문서 중복과 문맥 예산을 고려해 근거 선택 → Ollama에 근거와 출처 전달 → 답변.

초기값은 검증 전 후보다. 코퍼스보다 k가 크면 가능한 개수로 제한한다.
- RRF k=60, 동일 가중치.
- 제목·문단 경계를 우선하고, 긴 문단은 E5 토크나이저 기준 본문 약 200~300토큰, overlap 약 30토큰에서 시작한다.
- 제목·prefix·특수 토큰을 포함한 실제 E5 입력이 512를 넘지 않게 검사한다.
- 지역·문서·시설을 가로질러 하나의 청크를 만들지 않는다. 위치·문서 제목·청크 순서를 유지한다.
- 근거는 3~5개 이내를 출발점으로 하되 고정 개수를 강제하지 않는다. Qwen 토크나이저 기준 검색 근거 총량 약 1200~1600토큰을 예산 후보로 둔다.
- 생성 문맥 4096에서 시스템·대화·도구 스키마·질의·출력 예약을 뺀 실제 잔여량을 먼저 계산한다. E5 토큰 수를 Qwen 토큰 수로 가정하지 않는다.
- 첫 단계에서 질문 자동 확장·요약·LLM reranking은 넣지 않는다. 검색 조합의 효과를 먼저 분리한다.

청크에는 doc_id, chunk_id, 본문, 제목, source_url, 수집 시점, 원문 갱신 시점(알려진 경우), 지역, 원문 hash와 사용 조건을 기록한다. 모델 revision·패키지 버전·분할·토큰화·임베딩 설정이 바뀌면 인덱스 버전을 바꾸고 재생성한다.

BM25 k1/b와 전처리, dense 정규화, 후보 수 등은 설정으로 남긴다. 검색 방식이 다르더라도 원문·청크·평가 질의를 같게 유지한다.

## 6. 어떤 여행 자료를 넣을 것인가

이번 문서는 검색 설계를 정하는 문서이며 코퍼스 출처를 확정하지 않았다.

첫 수집 대상은 국내 관광지 설명·이용 안내·교통 접근 정보 등 출처와 이용 조건을 확인할 수 있는 공식 자료다. “공개 웹페이지”라는 이유만으로 본문을 GitHub에 재배포하지 않는다. 각 출처의 수집·저장·공개 조건을 확인하고, 허용되지 않으면 원문 제외와 재수집 절차 또는 자체 작성 자료를 사용한다.

학습용 소규모 합성 자료는 별도 fixture로 표시한다. 실제 여행 추천의 증거로 혼용하지 않는다. 여행 후기의 주관적 평가와 기관 안내를 출처 유형으로 구분한다.

실시간 숙박비·예약 가능 여부·날씨·운행 시각은 정적 문서 RAG만으로 보장하지 않는다. 나중에 별도 API 도구로 조회하거나 미확인으로 표시한다. 문서의 과거 가격과 현재 가격을 구분한다.

“차 없이 갈 수 있다” 같은 조건은 점수만 높다고 충족된 것이 아니다. 자료의 실제 근거를 확인해야 한다. 명시적인 메타데이터가 있는 조건만 확실한 필터로 쓰고, 모르는 조건을 false로 바꾸지 않는다.

## 7. 검색을 평가한 뒤 생성·에이전트로 연결한다

기존 Q01~Q10은 대화·조건 준수 평가다. 전부 미정인 Q01은 정답 근거가 명확한 검색 평가 질의가 아니므로 RAG 검색 점수 계산에 그대로 쓰지 않는다.

별도 검색 평가 질의 20~30개를 제안한다. 지역·시설명 정확 일치, 띄어쓰기·조사 변형, 의미적 우회 표현, 두 조건 결합, 비슷하지만 틀린 문서, 코퍼스에 없는 정보가 섞이게 한다. 답이 없는 질의는 일반 Recall/nDCG 집계에서 분리한다.

사람이 정답 근거와 doc_id·chunk_id를 지정하고 관련성 0(무관)·1(일부)·2(직접 근거)를 판정한다. 여러 검색기의 후보를 모아 검토하되 pooled label이 누락될 수 있다는 한계를 기록한다. 같은 장소의 인접·중복 청크 때문에 점수가 부풀지 않게 문서 수준 결과도 본다. 개발용 질의와 보류 질의를 나누고 보류 결과를 보고 튜닝했으면 다시 보류라고 부르지 않는다.

동일한 corpus snapshot·chunk manifest로 비교:
- A: BM25 only.
- B: Dense only.
- C: BM25 + dense + RRF.
- D: C와 동일한 후보를 받아 reranking.
- 필요 시 추가 비교: BM25+rerank, dense+rerank. 같은 reranker와 후보 예산을 유지한다.

지표:
- Recall@20: 사람이 라벨링한 관련 근거 중 후보가 얼마나 포함하는가. 불완전 qrels에서는 측정된 라벨에 대한 recall임을 명시한다.
- nDCG@5: 관련성 등급을 고려해 직접 근거를 상위에 배치하는가.
- MRR@5: 직접 근거 등급 2의 첫 등장 순위. 보조 지표로 사용한다.
- 검색·질의 임베딩·RRF·리랭킹의 지연과 전체 지연, CPU/RAM·VRAM, 인덱스 크기.
- cold load와 warm 요청을 분리하고 소규모 표본의 p95를 운영 SLA로 해석하지 않는다.

그다음 같은 Ollama 모델·생성 설정으로 근거 있는 주장, 인용의 실제 뒷받침, 불확실성 고지와 사용자 선택 도움을 확인한다. 무근거 답변·가짜 출처를 별도 실패로 집계한다. 생성 결과가 좋다는 이유로 검색 누락을 숨기지 않는다.

초기에는 사람이 채점한다. 자동 LLM judge나 RAGAS를 먼저 도입하지 않으며, 필요해지면 수동 라벨과의 일치·비용을 확인한다. threshold는 개발 질의에서 검증하며 cosine·RRF·reranker 점수에 공통 임계값을 적용하지 않는다.

개선이 없더라도 실험 결과는 남긴다. 학습용으로 모든 경로를 구현하되 실제 서비스 기본 경로는 품질·지연·유지 비용으로 결정한다. 아직 성능 목표 숫자나 개선률을 관측한 것처럼 쓰지 않는다.

## 8. 에이전트에 어떻게 연결할 것인가

검색기와 근거 기반 답변을 먼저 독립 CLI에서 실행한다. 이후 search_travel_documents(query, filters, top_k)를 읽기 전용 도구로 노출한다. 모델은 필요에 따라 도구를 호출하고 검색 결과를 읽어 다음 행동을 정한다.

도구는 답변을 대신 완성하기보다 chunk_id·원문 근거·출처·시점·검색 모드·관찰 가능한 점수를 반환한다. 출처 문서는 데이터이며 그 안의 문장을 시스템 지시처럼 실행하지 않는다.

시스템 프롬프트는 여행 지원 역할·도구 사용·근거와 미정 정보의 구분을 간결하게 정한다. 출발지를 먼저 물어야 한다는 식의 고정 대본을 검색기 안에 넣지 않는다. 이전 연구일지 005의 문구는 참고 사례로 남기되 첫 구현을 대화 정책 설계부터 시작한다는 우선순위는 이 문서로 수정한다.

## 9. 이번에 내린 권고와 확정할 항목

권고 구현안:
Python → Kiwi + rank_bm25 → multilingual-e5-small/CPU + NumPy exact search → RRF → bge-reranker-v2-m3/CPU → Ollama Qwen3.5 4B.

선택 이유: 한국어 lexical 전처리와 dense 검색을 분리해서 관찰하고, 학습 목표인 fusion·reranking을 구현하면서 GPU 메모리 경쟁과 초기 서버 운영 복잡성을 제한하기 위해서다. 최신 모델의 우월성이나 이 장비의 처리 속도는 아직 검증하지 않았다.

이 문서에서 확정하고 싶은 것은 “하이브리드 검색과 별도 리랭킹까지 비교 가능한 작은 RAG를 먼저 만든다”는 방향이다. 위 모델·후보 수·청크 길이는 첫 실험값이며 실패하면 교체한다. 코퍼스 출처·재배포 조건, 설치 가능 버전, CPU 지연은 다음 작업에서 확인한다.

사용자가 이 방향을 확인하면 다음 순서로 진행:
1. 사용 조건을 확인한 소규모 코퍼스와 소수 qrels 준비.
2. BM25·dense 검색과 인덱스 재현 절차 구현.
3. RRF·리랭커를 연결하고 A~D 비교.
4. 근거 기반 생성과 인용 확인.
5. 에이전트의 조회 도구로 연결.

이번 작업은 문서 검토까지다. 자료와 패키지를 설치하거나 구현이 끝났다고 표시하지 않는다.

## 10. 근거와 재현성 기록
