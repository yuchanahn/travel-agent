# 사람이 읽는 포트폴리오의 편집·시각 구성·PDF 제작 규칙

상태: 적용 중
검토일: 2026-10-25
근거: 사용자의 이번 편집 지시. 토스 두 지원 서류는 자유양식 PDF로 제출한다는 사용자 제공 조건을 작업 전제로 삼는다. 온라인 제출 규격을 별도 확인한 기록은 아니다.

## 목표와 독자

목표는 가진 재료로 공고의 요구에 답하는, 사람이 편하게 읽는 서류다. 독자는 구현·기술·기여를 짧은 설명과 시각 자료로 이해할 수 있어야 한다. 연구 기록의 완전성이나 설명의 양을 제출 문서의 품질로 취급하지 않는다.

## 본문에 무엇을 쓸 것인가

- 만든 기능과 설계 의도를 먼저 설명한다. 기술명은 해당 기능·구조와 붙여 짧게 보여준다.
- 사용자가 무엇을 할 수 있는지, 어떤 문제를 고려했는지, 어떤 선택을 했는지를 구체적인 장면으로 전달한다.
- 확장·운영·사용자 평가를 고려한 이유가 실제 연구와 설계에 있으면 그 판단을 적극적으로 보여준다. 해당 배경의 근거를 확인하고, 설계 의도와 운영 실적을 구별하는 정확한 동사를 선택한다.
- “대규모 사용자는 아니다”, “외부 트래픽은 없다”, “혼자 포폴용으로 만들었다”, “테스트는 실패했으며 성과로 포장하지 않겠다” 같은 부정적 해명을 본문에 자발적으로 반복하지 않는다.
- “로컬 운영”, “금융 규정 미구현” 등의 내부 확인 항목을 모든 파트의 필수 단서로 붙이지 않는다. 제목과 설명이 실제 경험을 넘어서는 인상을 만들면 문장 자체를 정확하게 고친다.
- 결과를 수치로 인용하는 경우 그 결과를 이해하는 데 꼭 필요한 조건만 짧게 붙인다. 모든 실패와 미실험 항목을 제출 본문에 나열하지 않는다. 세부 실험 기록은 연구일지에 보존한다.
- 실제 하지 않은 운영·협업·성과를 만들어내지 않는다. 검토용 사실 확인과 독자에게 보여줄 설명을 분리한다.

예를 들어 요청 대기·예산·복원 기능을 다루는 파트는 “요청이 몰리거나 실행이 중단되는 상황을 고려해 대기열·호출 예산·상태 복원을 설계했다”처럼 실제 선택을 설명한다. 이 예문은 표현 방식의 참고이며, 실제 구현·설계 이유와 대조한 뒤 사용한다.

## 사진·다이어그램·기술명의 전개

1. 각 파트가 전달할 핵심을 한 문장으로 정한다.
2. 기존 이미지 중 그 문장을 가장 빨리 이해시키는 화면이나 설명도를 고른다. 자료가 있다는 이유만으로 전부 넣지 않는다.
3. 사진·다이어그램이 보여줄 범위를 정한 다음 제목·기술명·짧은 설명을 배치한다. 본문과 그림 설명을 반복하지 않는다.
4. 그림 안 글자가 읽히도록 크기·크롭·주석을 조절한다. 복잡한 전체 구조도는 필요한 흐름으로 나눠 보여준다.
5. 페이지마다 강조할 핵심이 보이게 하고 여백·정렬·제목 단계·글꼴·색을 일관되게 쓴다.

전체의 출발점은 “무엇을 만드는가”를 보여주는 제품 화면이다. 이후 공고별 주장에 맞춰 사용 흐름·구조·메모리·추적·평가 장면을 전개한다. 공고1과 공고2의 순서가 같아야 할 이유는 없다. 페이지 수·이미지 수·코드 수를 미리 고정하지 않는다.

## Notion 초안 → 요청 시 별도 PDF

먼저 Notion에서 내용·그림 선택·순서·문구를 구성하고 사용자와 검토한다. Notion은 편집 원본이다. 상세 코드 토글과 링크는 보조 자료로 쓰되 본문 이해의 필수 경로로 만들지 않는다.

사용자가 “이 Notion 페이지로 PDF를 만들어줘”라고 요청하면 해당 페이지의 최신 내용을 읽고 PDF 지면에 맞게 별도로 조판한다. Notion 기본 PDF 내보내기를 최종 제작 방식으로 삼지 않는다. 내용의 의미는 유지하면서 정보 배치·그림 크기·여백·타이포그래피·페이지 나눔을 더 읽기 좋게 다듬는다.

PDF에서는 토글·긴 웹 페이지·스크롤에 기대지 않는다. 잘리는 표·이미지·고립된 제목·지나치게 작은 코드/글씨를 확인하고, 한글 글꼴과 텍스트 선택/검색 가능 여부를 점검한다. 페이지를 렌더링해 실제 배치와 가독성을 눈으로 확인한다. 제작 단계에는 PDF 스킬을 적용한다.

현재 요청은 편집 방향의 확정과 규칙 반영이다. 이 단계에서 PDF 제작이나 기존 포트폴리오 전면 개편을 시작하지 않는다.

## 검토 기준

“원하는 인재로 읽히는가”, “기술을 쉽게 이해하는가”, “눈으로 따라가기 편한가”를 함께 검토한다. 자료량·숫자·디자인 취향만으로 작성 에이전트가 완성도를 확정하지 않는다. 과거 공고 분석의 경험 확인 항목은 작성자 내부 자료이며 제출 본문으로 자동 복사하지 않는다.
