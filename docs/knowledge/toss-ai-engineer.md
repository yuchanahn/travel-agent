# 공고1 · 토스 AI Engineer 요구와 인재상

상태: 적용 중 — 서류 전략 가설
검토일: 2026-10-25
근거: 사용자 제공 공고1의 팀 소개·업무·자격·이력서 안내·동료 메시지. 공고 밖의 심사 기준은 추정하지 않았다. 공통 편집 기준은 [서류 설계 기준](toss-hiring-brief.md).

## 먼저 만들어야 할 인재상

**고객의 모호한 요청을 이해하고, 필요한 정보와 도구를 연결해 실제 문제 해결로 이어지는 에이전트를 설계하며, 불확실한 행동을 실험과 평가로 개선하는 사람.**

이는 목표 인재상이며 지원자가 이 모든 경험을 보유했다는 소개문은 아니다. 팀이 원하는 최종 결과는 모델을 호출하는 기능이 아니라 고객과 상호작용하며 일을 수행하는 서비스다. 서류는 그 일을 설계하는 판단을 보여줘야 한다.

## 공고를 요구 단위로 해체

원문 위치는 사용자가 제공한 공고의 소제목을 가리킨다. “명시”는 문구의 요약, “해석”은 그 요구가 서류에서 어떤 모습으로 읽혀야 할지에 대한 가설이다.

| 원문 위치·표현 | 명시된 요구 | 서류에서 보여줄 모습에 대한 해석 |
| --- | --- | --- |
| 팀 소개 · 의도와 맥락, RAG, Tool Calling | 대화 이해·정보 탐색·서비스 실행으로 고객 문제 해결 | 질문에 답한 뒤 사용자가 무엇을 결정/실행할 수 있게 됐는지까지 설계하는 사람 |
| 팀 소개·업무 · 텍스트·이미지와 실시간 음성 | 멀티모달 맥락 활용, 음성의 끼어들기·전환·침묵, 저지연 대화 | 입력과 환경의 특성에 맞게 에이전트 구성을 바꾸는 사람 |
| 업무 · 프롬프트·RAG·Context·Eval·Tool·Guardrail | 목적 달성을 위한 장치 설계와 실험 | 각 기술을 어떤 실패를 다루기 위해 선택했는지 말할 수 있는 사람 |
| 업무·자격 · 확률적 컴포넌트, 정량 평가 | 데이터셋·지표·가드레일·검증과 반복 개선 파이프라인 | “응답이 나왔다”와 “목적을 달성했다”를 구별하고 개선 판단을 내리는 사람 |
| 업무 · 고객 피드백과 비즈니스 지표 | 실제 피드백·성과에서 개선점 발견 | 사용자 행동과 제품 성과를 기준으로 개발 우선순위를 정하는 사람 |
| 자격 · 문제 정의부터 설계·실험·평가 전체 주도 | 전체 문제 해결 과정의 주도 경험 | 도구에 지시한 일 목록보다 본인이 정한 문제·대안·선택이 보이는 사람 |
| 자격 · Multi-Agent·LLM·RAG·멀티모달 등 | 최신 AI를 복잡한 비즈니스 문제에 활용 | 유행 기술을 많이 붙이는 것보다 과제에 맞는 구성을 설명하는 사람 |
| 업무·자격 · 적용 가능성·확장성·지속 가능성 | 서비스로 이어지는 설계 | 동작하는 데모 이후의 제약과 운영 비용을 함께 판단하는 사람 |
| 자격 · 품질·지연 시간·비용 | 트레이드오프 이해·선택·최적화 경험 | 한 지표만 최대화하지 않고 선택의 대가를 설명하는 사람 |
| 자격 · 다양한 형태의 데이터 | 텍스트·이미지·음성·구조화 데이터 통합 활용 | 입력을 수집한 뒤 모델이 쓸 수 있는 맥락과 행동으로 연결하는 사람 |
| 이력서 안내·동료 메시지 | 영향, 제약→정의→실험→평가→개선, 협업 역할, 고객 관점 zero to one | 이 팀에서 맡을 수 있는 문제와 일하는 방식이 드러나는 사람 |

## 강도와 예외를 읽는 법

음성 경험이 없어도 텍스트·이미지 기반을 포함한 프로덕션 수준 에이전트 개발·반복 개선 경험이 있다면 충분하다고 명시한다. 따라서 음성 부재만으로 스스로 탈락 판정을 내릴 이유는 없다. 동시에 이 문장이 멀티모달·프로덕션·반복 개선 요구까지 없애는 것은 아니다.

Multi-Agent·LLM·RAG·멀티모달은 활용 경험의 예시로 함께 제시됐다. 모든 기술을 각각 필수 구현하라는 체크리스트로 바꾸지 않는다. 팀이 여러 분야 전문가와 협업한다는 설명과 이력서의 역할 안내는 실제 협업 판단을 보여줄 기회이지, 개인 프로젝트를 팀 프로젝트로 꾸밀 근거가 아니다.

## 여행 프로젝트에서 먼저 읽히게 할 것

**중심 주장 후보:** 사용자의 조건이 계속 바뀌는 조사 과정을, 문맥을 이어가며 근거를 찾고 사용자가 편집·결정할 수 있는 제품 흐름으로 설계했다.

이 문장은 후속 포트폴리오의 방향 후보이며 사용성 향상을 측정했다는 주장은 아니다.

사례 선택의 중심은 고객의 의도를 이어받는 설계, 필요한 근거를 행동으로 연결하는 설계, 그 행동을 평가해 고치는 판단이다. 멀티모달·음성·최적화는 공고에 있는 별도 요구로 남겨 두고 실제 보유 경험으로 연결한다. 없는 경험을 채우기 위해 본론을 기술 도입 계획으로 바꾸지 않는다.

| 보여줄 장면 | 연결되는 요구 | 그 장면에서 드러낼 판단 | 확인할 기존 자료 |
| --- | --- | --- | --- |
| 여행 요청 뒤 예산·인원을 수정하고 계획서를 고침 | 의도·문맥 이해, 고객 문제 해결 | 모든 조건을 다시 입력하게 하지 않고 최신 정정을 이어 쓰게 한 이유 | [계획서](../travel-plan.md), [웹 대화](../web-interface.md) |
| 요약에 없는 과거 선택 이유를 원문에서 찾음 | Context Engineering·RAG | 요약과 원문을 다른 역할로 보존하고 검색으로 보완한 이유 | [메모리](../memory-rag.md), [메모리 실험](../research/2026-10-23-082-memory-eval-and-monitoring.md) |
| 모델의 검색 선택과 실제 도구 실행을 연결함 | Tool Calling·목적 달성 장치 | 모델이 행동을 정하되 실행기는 허용 범위·예산·실패를 관리하는 역할 분리 | [실행 구조](../../ARCHITECTURE.md), [MCP](../mcp.md) |
| 수집/전달 실패와 모델의 근거 사용 실패를 나눠 봄 | 실험 설계·평가·개선 | 무엇을 바꾸면 어떤 실패가 달라질지 원인을 분리하는 방식 | [검색/계획 보완](../research/2026-10-24-094-search-plan-reliability.md), [품질 한계](current-state.md) |
| 로컬 모델·문맥 예산·검색 전달량을 선택함 | 품질·지연·비용 판단 | 제약 아래 어떤 선택을 했고 무엇을 아직 측정하지 않았는지 | [공급자](../llm-providers.md), [압축 정책](../research/2026-10-24-096-conservative-context.md) |

기존 수치나 상세 로그는 위 주장에 필요한 자료만 꺼낸다. 세션 수·테스트 총량·토큰 한도를 중심 역량처럼 도입하지 않는다. “사용자의 조건을 이어받아 계획서로 연결했다”와 “추천의 사실 정확도가 향상됐다”는 별도 주장이다.

## 두 서류가 맡을 역할

**포트폴리오:** 사용 상황 → 사용자가 할 수 있는 일 → 핵심 설계 판단 → 그 판단을 확인한 대표 사례 순서가 후보가 된다. 도구 전체 목록 대신 문맥·행동·계획서가 이어지는 실제 흐름을 중심에 둔다. 연구 과정은 선택 이유를 이해하는 데 필요한 만큼만 포함한다.

**자기소개서:** 어떤 불편을 문제로 봤는지, 왜 그 구성으로 풀었는지, 막혔을 때 무엇을 분리해 판단했는지로 주도성과 일하는 방식을 설명한다. 실제 회사 지원 동기·팀 협업 경험은 확인된 개인 이력이 있을 때 연결한다. 여행 도메인을 금융 고객 업무로 그대로 치환하지 않는다.

## 작성자 내부 확인 · 제출 본문에 자동 삽입하지 않음

이 절은 근거를 대조하는 내부 메모다. 경험 부재와 실패를 나열하는 제출 문단으로 사용하지 않는다. 본문은 실제 기능과 설계 판단을 쉬운 설명과 시각 자료로 보여준다. [편집 규칙](portfolio-presentation.md)을 우선 적용한다.

이 프로젝트만으로 멀티모달/음성 모델 설계·고객 트래픽 운영·실제 비즈니스 지표 개선·조직 협업을 입증하지는 못한다. 다른 실제 경험이 있으면 나중에 연결한다. 없으면 텍스트 에이전트에서 한 설계의 가치를 구체적으로 보여준다. 비슷한 미래 기능을 급히 추가해 공고의 키워드를 채우는 것을 기본 전략으로 삼지 않는다.

실제 추천 품질의 열린 실패는 [현재 상태](current-state.md)에 있다. 개선 사례를 선택할 때 기능 보완과 사실 품질 개선을 섞지 않는다. 한계를 본문의 주인공으로 만들 필요는 없지만, 그 한계 때문에 성립하지 않는 성공 문장을 쓰지는 않는다.

## 후속 원고를 판단할 핵심 질문

읽은 사람이 “고객 문제를 에이전트의 문맥·행동·평가 설계로 옮길 수 있는 사람”이라고 이해하는가? “여러 검색 기술을 공부하고 실험 기록을 많이 남긴 사람”이라는 인상에 머문다면 사례 선택과 설명 순서를 다시 잡는다.
