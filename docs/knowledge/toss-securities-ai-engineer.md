# 공고2 · 토스증권 AI Engineer 요구와 인재상

상태: 적용 중 — 서류 전략 가설
검토일: 2026-10-25
근거: 사용자 제공 공고2의 WM 팀 소개·업무·자격·우대·이력서 안내. 공고 밖의 심사 기준은 추정하지 않았다. 공통 편집 기준은 [서류 설계 기준](toss-hiring-brief.md).

## 먼저 만들어야 할 인재상

**에이전트의 행동·메모리·도구·데이터 흐름을 서비스 구조로 설계하고, 실제 사용자 환경에서 그 과정을 관찰·평가·운영하며 신뢰할 수 있는 제품으로 개선하는 사람.**

이는 목표 인재상이며 현재 지원자의 보유 경력을 확정한 문장이 아니다. WM의 투자 전략 플랫폼이라는 맥락 때문에 “모델이 말을 잘함”을 넘어 정보의 출처·조건·오류·행동 권한을 다룰 수 있는지가 서류에서 중요하게 읽힐 가능성이 있다.

## 강도와 예외를 읽는 법

대규모 사용자 운영과 프로덕션 기본기는 “함께하고 싶어요”에 있다. 단순 우대사항으로 낮춰 읽지 않는다. 반면 금융 서비스 경험·개인 투자 관심은 우대사항이다. 금융 경력이 없다는 이유만으로 전체 자격이 없다고 확정하지 않는다.

멀티 에이전트와 라우터는 실제 업무에 명시돼 있다. 그렇다고 단일 에이전트의 병렬 도구 호출을 멀티 에이전트 경험으로 이름만 바꾸지 않는다. 현재 구조에서 설명할 수 있는 경계를 보여주고 추가 보유 경험을 따로 찾는다.

## 여행 프로젝트에서 먼저 읽히게 할 것

**중심 주장 후보:** 모델의 자율적인 행동을 실행 경계·메모리·관측·평가와 연결해, 요청의 처리 과정과 결과를 관리할 수 있는 에이전트 제품 구조를 만들었다.

이 문장은 구현된 로컬 제품 구조에 대한 방향 후보다. 대규모 서비스 운영 경력이나 금융 규정 준수를 뜻하지 않는다.

사례 선택의 중심은 요청을 관리하는 구조, 실패를 관찰하고 수정할 수 있는 구조, 사용자에게 제공할 결과의 신뢰 경계다. 데이터·평가·운영 항목은 이 구조가 왜 필요했는지를 설명할 때 연결한다. 공고의 용어를 소제목으로 모두 옮기는 방식은 구성 후보 중 하나일 뿐이다.

| 보여줄 장면 | 연결되는 요구 | 그 장면에서 드러낼 판단 | 확인할 기존 자료 |
| --- | --- | --- | --- |
| 요청→모델→도구→다음 입력→저장/종료의 실행 경로 | 오케스트레이션·구조 설계 | 확률적 행동과 실행기의 보장 범위를 어떻게 나눴는가 | [구조 지도](../../ARCHITECTURE.md), [하네스 설명](../portfolio/01-harness.md) |
| 검색 요청·반환·다음 모델 입력을 연결해 오류를 추적 | Observability·trajectory | 마지막 답변만 보고는 알 수 없는 실패를 어디서 구분했는가 | [평가·관측](../portfolio/03-evaluation-observability.md) |
| 원문·요약·검색 결과와 대화 분기를 관리 | Memory 미들웨어 | 과거 근거를 유지하면서 다른 분기와 섞이지 않게 한 이유 | [메모리](../memory-rag.md), [문맥 관리](../research/2026-10-23-093-runtime-context.md) |
| 호출 예산·대기·저장·재시작·삭제를 다룸 | 프로덕션 기본기 | 실패하거나 중단돼도 어떤 상태를 보존하고 무엇을 사용자에게 알리는가 | [제품 흐름](../portfolio/04-product-reliability.md), [웹 운영](../web-interface.md) |
| 출처·원문·선별된 발췌를 구분해 모델에 전달 | 데이터 검증·정제 | 크기를 줄일 때 출처·조건·필요한 정보를 어떻게 유지하려 했는가 | [문서 수집](../web-documents.md), [검색 선별](../research/2026-10-24-094-search-plan-reliability.md) |
| 계획 초안·직접 수정·선택 확정의 권한을 분리 | 신뢰·사용자 통제 | 모델의 제안이 사용자의 확정이나 실제 거래로 혼동되지 않게 한 방식 | [계획서](../travel-plan.md) |
| 실행 성공과 목적에 맞는 답변을 별도로 평가 | Eval·루프 엔지니어링 | 어떤 실패를 발견했고 어떤 수정만 효과를 확인했는가 | [인수 기준](../acceptance-testing.md), [현재 한계](current-state.md) |

웹 자료의 수집·정제를 금융 데이터 파이프라인 구축 경력으로 바꾸지 않는다. 가격·시설의 조건과 출처를 보존하려 한 설계는 유사한 문제를 다루는 사고방식으로 설명할 수 있다. 금융 제품에 적용하려면 다른 검증·통제가 필요하다는 경계는 유지한다.

## 두 서류가 맡을 역할

**포트폴리오:** 어떤 사용자 작업을 지원하는 제품인지 짧게 설명하고, 요청의 전체 구조 → 관측 가능한 실행 → 문맥/데이터/행동 경계 → 평가와 개선 판단 순으로 전개하는 구성이 후보가 된다. 운영 항목은 기능 이름보다 실패·복구·일관성의 이유를 보여준다. 기존 여섯 파트를 그대로 복제할 필요는 없다.

**자기소개서:** 기능을 만드는 데서 어디까지 책임지려 했는지, 실패를 추적해 문제 범위를 어떻게 좁혔는지, 사용자에게 맡겨야 할 결정과 모델에 맡길 판단을 어떻게 나눴는지 설명한다. 금융 지원 동기는 확인한 실제 경험이나 관심이 있을 때 연결한다. 여행 준비 경험만으로 투자 자문 전문성이나 고객 자산 운영 경험을 주장하지 않는다.

## 작성자 내부 확인 · 제출 본문에 자동 삽입하지 않음

이 절은 근거를 대조하는 내부 메모다. 제출 본문에는 실제 구현·판단·운영을 고려한 설계 이유를 간단하게 보여준다. 아래의 경험 부재를 자발적인 해명 문구로 옮기지 않는다. [편집 규칙](portfolio-presentation.md)을 우선 적용한다.

이 프로젝트는 로컬 제품의 실행 구조·미들웨어·추적·사용자 통제 경험을 보여준다. 공고의 대규모 대고객 운영 요구를 대신 충족시키지는 않는다. 그 간극은 표현만으로 없앨 수 없다. 다른 실제 서비스 운영 경력이 있는지는 아직 모른다. 후속 작성에서 확인해 별도 사례와 연결할 항목이다.

금융 도메인·컴플라이언스 조직 협업·멀티 에이전트·라우터 구축도 현재 프로젝트에서 입증한 경력과 구분한다. 사용자가 제어하는 확정 절차를 금융 컴플라이언스 구현으로 이름 붙이지 않는다. 필요한 부분의 범위를 정직하게 설명하면서, 이 프로젝트가 가장 잘 보여주는 시스템 설계 판단에 본문의 공간을 쓴다.

## 후속 원고를 판단할 핵심 질문

읽은 사람이 “에이전트의 실행을 이해하고, 상태·데이터·품질·사용자 통제를 함께 설계하는 사람”이라고 이해하는가? “로컬 챗봇을 만들고 테스트를 많이 돌린 사람”에 머문다면 구조와 책임 범위를 보여주는 사례를 다시 고른다. 운영 경험이 실제로 확인되지 않았는데 “대규모 서비스도 맡겨도 된다”는 결론을 문장만으로 만들어내지 않는다.
