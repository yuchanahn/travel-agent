# 토스 두 공고의 서류 설계 기준

상태: 적용 중 — 공고 해석과 서류 전략은 초안
검토일: 2026-10-25
근거: 사용자가 이 대화에 제공한 토스 AI Engineer 공고1·토스증권 AI Engineer 공고2 전문. 프로젝트 대조 기준은 e7361ac의 공개 문서. 온라인 최신 공고·내부 심사표를 확인한 자료는 아니다.

## 이번 작업의 목적

각 공고에서 필요로 하는 인재상을 먼저 도출하고, 그 인재로 읽히도록 경험의 선택·배치·언어를 설계한다. 기술·실험 기록을 모두 보여주는 것과 채용 서류로 설득하는 것은 다르다. 이번 산출물은 공고 분석과 후속 작성 기준이며 포트폴리오·자기소개서 완성본이 아니다.

공고는 답안이 충족해야 할 공개 요구사항으로 다룬다. 실제 심사 배점·합격 답안은 공개되지 않았으므로 아래 우선순위와 인재상은 문구에 근거한 전략 가설이다. 작성 에이전트가 “잘 썼다”, “100점이다”라고 자체 확정하지 않는다.

## 두 공고의 결정적인 차이

| 질문 | 공고1 · 토스 | 공고2 · 토스증권 WM |
| --- | --- | --- |
| 고객에게 만들고 싶은 변화 | 자연스러운 상호작용을 통해 고객의 문제를 풀고 실제 비즈니스를 수행 | 투자 전략 플랫폼에서 고객에게 신뢰할 수 있는 에이전트 서비스를 제공 |
| 핵심 엔지니어링 과제 | 불확실한 모델의 문맥 이해·행동·대화를 설계하고 실험으로 개선 | 오케스트레이션·메모리·추적·데이터·평가·서빙을 제품으로 묶고 운영 |
| 원하는 인재상에 대한 해석 | 고객 문제를 에이전트의 행동 설계와 개선으로 전환하는 제품 지향 AI 엔지니어 | 에이전트를 관찰·통제·평가하면서 서비스로 운영하는 제품 지향 AI 시스템 엔지니어 |
| 여행 프로젝트의 앞부분 | 왜 여행 준비가 불편했고, 조건 정정·근거 탐색·계획서가 이를 어떻게 다루는가 | 사용자 요청부터 도구·문맥·저장·실패까지 어떻게 관리하고 확인할 수 있는가 |
| 강하게 확인할 대목 | 문제 정의·기술 선택·실험/평가·품질/지연/비용 판단 | 실제 사용자 환경·운영 기본기·trajectory·평가 기반 개선·금융 데이터 신뢰 |

차이는 강조점이다. 공고1도 프로덕션과 정량 평가를 요구하고, 공고2도 고객 경험과 기술 선택 이유를 요구한다. 한쪽을 연구직, 다른 쪽을 단순 서버직으로 구분하지 않는다.

## 다음 작업의 읽기 순서

1. [공고1의 요구와 인재상](toss-ai-engineer.md) 또는 [공고2의 요구와 인재상](toss-securities-ai-engineer.md)을 먼저 읽는다.
2. 공고별로 “이 사람을 왜 이 팀에 불러야 하는가”에 대한 중심 주장을 하나 정한다.
3. 그 주장을 보여줄 프로젝트 장면과 설계 판단을 고른다. [프로젝트 소개](../../README.md), [현재 포트폴리오](../portfolio/travel-agent-draft.md), [구조 지도](../../ARCHITECTURE.md)를 자료로 쓴다.
4. 포트폴리오는 구현과 작동을 보여주고, 자기소개서는 문제를 보는 관점·선택·주도성을 설명한다. 같은 설명을 두 서류에 복제하지 않는다.
5. 검토 시 공고 문구와 실제 경험에 비춰 수정한다. 사용자가 검토하기 전에는 최종본으로 취급하지 않는다.

## 후속 작성에 적용할 편집 원칙

- **인물과 기여가 먼저다.** 무엇이 불편했고, 무엇을 직접 정의·선택·설계했으며, 그 결과 무엇을 사용할 수 있게 됐는지 연결한다.
- **기술은 판단의 이유다.** BM25·RRF·MCP·trace를 알고 있다는 사실보다 그 장면에서 왜 필요했는지 설명한다.
- **포장은 선택·순서·번역이다.** 같은 사실을 직무의 문제 언어로 설명한다. 사용자 수·매출·금융 경력·협업·멀티모달·대규모 운영을 새로 만들어내지 않는다.
- **수치는 주장에 필요한 만큼 쓴다.** 독자의 판단을 바꾸는 비교에만 붙인다. 테스트 총량·호출 횟수·토큰 예산을 본문 도입이나 개인 역량의 대리 지표로 쓰지 않는다.
- **정량 평가는 지우지 않는다.** 두 공고 모두 평가를 요구한다. 무엇을 좋은 답변으로 정의했고 어떤 선택을 검증했는지가 먼저고, 필요한 수치와 조건은 그다음이다.
- **한계는 주장 가까이에 필요한 만큼 둔다.** 도입을 미구현 목록으로 시작하지 않는다. 특정 성과를 쓸 때 그 성과의 범위를 정확히 한정한다. 핵심 결론을 바꾸는 실패는 숨기지 않는다.
- **고객 가치와 사업 성과를 구분한다.** 반복 입력·조사 맥락·결정 과정의 불편을 해결하려는 설계는 설명할 수 있다. 실제 사용성·전환·비용 개선을 측정한 성과처럼 쓰지는 않는다.
- **기존 양식은 재료다.** 이전의 여섯 역량 파트·사진/코드 개수는 기존 발표 본문의 구성이다. 두 지원 서류의 정답 틀로 자동 고정하지 않는다.
- **개인 기여는 정확하게 표현한다.** 개인 프로젝트의 문제 정의·구조 선택·검증 주도와 Codex를 활용한 구현 과정을 구분한다. 가상의 팀 협업이나 전 코드를 수작업한 경력을 만들지 않는다.

## 초안을 검토할 질문

| 검토 관점 | 확인할 질문 |
| --- | --- |
| 공고 적합성 | 이 문단은 이 팀의 어떤 업무에 투입할 수 있다는 판단을 돕는가? |
| 인물의 선명함 | 기술 이름을 지워도 지원자의 판단과 역할이 남는가? |
| 선택과 집중 | 공고1과 공고2의 첫 장·사례 순서가 실제로 다른가? |
| 구체성 | 구현 장면과 선택 이유가 보이는가? 자료 목록으로 끝나지 않는가? |
| 사실의 범위 | 보여준 결과가 해당 주장에 충분한가? 로컬을 서비스 운영 경력으로 확대하지 않았는가? |
| 독자 부담 | 근거를 찾으러 여러 링크를 열지 않아도 핵심 기여를 이해할 수 있는가? |
| 서류의 역할 | 포트폴리오와 자기소개서가 서로 다른 질문에 답하는가? |

이는 내부 심사표가 아닌 초안 검토 질문이다. 자동 점수·합격 확률·에이전트의 자기 칭찬으로 대체하지 않는다.

## 출처와 미확정 사항

공고의 직무·업무·자격·우대·이력서 안내는 사용자 제공 본문을 기준으로 고정했다. 채용 이벤트의 보상·마감·현재 접수 가능 여부는 분석하지 않았다. 지원 단계에서 필요하면 별도로 공식 안내를 확인한다.

프로젝트 외 경력·학력·이전 협업·지원 동기·개인 투자 경험·자기소개서 문항/분량은 이 자료만으로 알 수 없다. 실제 원고에 필요해질 때 사용자에게 확인한다. 개인 이력과 지원서 원문은 비공개 위치에서 관리하고, 여기에는 공개 공고와 공개 프로젝트에 기반한 분석만 남긴다.

분석 작업의 기록은 [100 연구일지](../research/2026-10-25-100-toss-hiring-analysis.md), 함께 읽을 문서는 [공고1](toss-ai-engineer.md)과 [공고2](toss-securities-ai-engineer.md)다.
