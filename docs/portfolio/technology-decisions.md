# 기술 선택 근거와 공고 매칭 · 작성용 검토 자료

기준: 2026-10-25, 제품 소스 b471ff5 및 아래 연구 기록. 시각 구성의 상세 본문으로 복사할 원고가 아니다. 실제 선택 이유와 현재 구현의 적합성을 구분한다. 모든 기술을 같은 조건에서 비교해 최적이라고 입증한 것은 아니다.

## 01 · Ollama·Qwen

- 문제와 선택: 외부 공급자에 의존하던 실행을 사용자 결정에 따라 기존 Ollama·설치된 Qwen 환경으로 복귀했다. 연구를 이어갈 실행 환경을 유지하는 선택이다.
- 판단 근거: [071 공급자 복귀](../research/2026-10-19-071-return-to-ollama.md)의 요청·공급자 오류·연결 확인. 타 모델 대비 품질 우위나 실제 비용 절감이 선택의 근거로 측정된 기록은 아니다.
- 기술의 역할: Ollama는 추론 제공 환경, Qwen은 행동·응답을 생성하는 모델이다. 제품 흐름 도입에 이름을 함께 표시한다.
- 공고 연결: 공고1의 제약 아래 서비스 구성·품질/지연/비용 판단, 공고2의 에이전트 애플리케이션 구조. 사용 모델 자체를 핵심 기여로 삼지 않는다.

## 02 · Codex·Claude Code·Brave Search MCP

- 문제와 선택: 검색 방식·원시 데이터 가공 연구를 에이전트에 나누고, 직접 검색의 접근·관련성 문제와 모델에 전달되는 자료를 검토해 Brave 공급자와 공식 MCP 통합으로 진행했다.
- 판단 근거: 역할 분담의 맥락은 사용자의 설명, 검색의 실제 경과는 [032 DuckDuckGo 중단](../research/2026-10-18-032-bing-only-search.md), [034 원시 결과 처리](../research/2026-10-18-034-search-evidence-pipeline.md), [042 Brave API 전환](../research/2026-10-18-042-brave-integration.md), [073 전달 자료 비교](../research/2026-10-20-073-live-harness-comparison.md), [074 공식 MCP 통합](../research/2026-10-20-074-official-brave-mcp.md).
- 대안과 대가: 직접 Bing/DuckDuckGo 요청을 유지·수리하는 방식과, 검색 공급자/표준 도구 연결을 사용하는 방식 사이의 선택이다. 개발 시간·유지 부담·비용·관련 후보와 발췌를 판단 항목으로 설명한다. 모든 엔진에 대한 통제된 시간·청구액 순위를 만들지 않는다. API 전환과 MCP 통합은 다른 시점의 결정이다.
- 공고 연결: 공고1의 실험·트레이드오프·서비스 적용, 공고2의 Tool Use·데이터 활용·설계 판단. Codex/Claude Code는 개발 협업의 도구이며 여행 제품 내부 멀티 에이전트로 그리지 않는다.

## 03 · BM25Plus·중복 제거

- 문제와 선택: 누적 검색 발췌·문서 목록으로 입력이 커졌다. URL 통합·출처 내 정확한 문장 중복 제거와 BM25Plus 선별을 적용하고 전달 예산을 뒀다.
- 판단 근거: [034 검색 파이프라인](../research/2026-10-18-034-search-evidence-pipeline.md), [093 입력 누적 진단](../research/2026-10-23-093-runtime-context.md), [094 검색 선별](../research/2026-10-24-094-search-plan-reliability.md). 원문은 별도 보존·색인해 선별에서 빠진 자료를 다시 찾게 한다.
- 대안과 대가: 원문 전체를 매번 전달하는 대신 관련 자료를 골라 전달한다. 선택 예산 때문에 누락될 수 있어 생략과 원문 재조회 경로를 관리한다. BM25Plus가 다른 랭커보다 우수하다는 비교로 표현하지 않는다.
- 공고 연결: 공고1의 Context Engineering·RAG·효율, 공고2의 비정형 데이터 정제·에이전트 활용 데이터 흐름.

## 04 · Tool Calling·MCP·실행 하네스

- 문제와 선택: 모델의 도구 요청을 실제 실행으로 연결하면서 허용 도구·인자·예산·병렬 결과·종료 상태를 관리해야 했다. 모델의 행동 선택과 실행기의 관리 책임을 나눴다.
- 판단 근거: [MCP 도입059](../research/2026-10-19-059-mcp-client-integration.md), [실행 하네스](01-harness.md), [구조 지도](../../ARCHITECTURE.md), `agent.run_agent/execute_batch/validate_call`.
- 대안과 대가: 외부 API를 고정 함수로 하나씩 복사하는 대신 서버의 도구/스키마를 발견해 허용 목록으로 연결했다. MCP 선택 이유와 실행기의 예산·추적 설계 이유를 분리한다. 별도 오케스트레이션 프레임워크와의 성능 우위를 근거 없이 붙이지 않는다.
- 공고 연결: 공고1의 Tool Calling·Guardrail, 공고2의 에이전트 구조·Tool Use·운영 안정성.

## 05 · SQLite·BM25 RAG·Context Engineering

- 문제와 선택: 요약에서 사라진 선택 이유를 요약만 다시 읽어서는 복원할 수 없었다. 원문을 보존하고 현재 대화 범위에서 관련 원문을 검색해 문맥을 보완한다.
- 판단 근거: [007 원문 RAG](../research/2026-10-17-007-conversation-memory-rag.md), [057 웹 원문 메모리](../research/2026-10-19-057-web-session-memory.md), [082 통제 비교](../research/2026-10-23-082-memory-eval-and-monitoring.md), [096 압축 정책](../research/2026-10-24-096-conservative-context.md).
- 기술별 이유: SQLite는 실제 원문·분기별 색인의 저장 기반이다. 이를 다른 저장소보다 우수해서 선택했다는 별도 비교 근거는 아직 확인하지 않았다. 웹 BM25 경로는 임베딩 추가 없이 원문 검색을 연결한 구현이며, CLI의 임베딩·RRF·리랭킹은 별도 학습·비교 경로다. 두 경로를 같은 제품 경로로 섞지 않는다.
- 대안과 대가: 요약만 유지하는 방식 대신 원문 보존·요약·검색을 분리한다. 저장·검색·요약의 역할이 늘어나는 만큼 범위와 실행 비용을 따로 관리한다.
- 공고 연결: 공고1의 RAG·Context Engineering, 공고2의 Memory 미들웨어·데이터/문맥 관리.

## 06 · JSONL Trace·Eval Harness

- 문제와 선택: 최종 답변만으로 검색 수집·도구 실행·전달·모델 해석 중 어디가 문제인지 알기 어려웠다. 호출 ID로 요청과 결과·다음 입력을 연결하고, 같은 질문과 평가 기준으로 변경을 확인한다.
- 판단 근거: [073 실제 호출 연결](../research/2026-10-20-073-live-harness-comparison.md), [077 독립 분석·원본 대조](../research/2026-10-20-077-rerun-failure-analysis.md), [082 실행 요약·평가](../research/2026-10-23-082-memory-eval-and-monitoring.md), [083 실행 비교](../research/2026-10-23-083-comparison-and-prompt.md).
- 기술별 이유: Trace를 연결해 원인을 추적하고, 고정 평가로 변경의 영향을 확인한다. JSONL은 이를 보존한 실제 형식이다. JSONL 자체를 다른 형식보다 우수하다고 비교한 기록과 혼동하지 않는다.
- 대안과 대가: 개별 답변의 인상만으로 판단하는 대신 실행 근거와 평가를 유지한다. 실제 개선을 주장할 사례는 비교 조건과 답변을 확인한 뒤 선택한다.
- 공고 연결: 공고1의 실험·정량 평가·개선 파이프라인, 공고2의 Observability·trajectory·Eval 데이터셋/하네스.

## 07 · Human-in-the-loop·JSON 계획서

- 문제와 선택: 일정·숙소·비용이 대화에 흩어져 다시 정리해야 했다. 대화 중 계획 초안을 저장하고 같은 데이터를 여러 화면에서 읽게 했다. 선택 확정은 사용자에게 둔다.
- 판단 근거: [090 계획서 도입](../research/2026-10-23-090-travel-plan.md), [094 자동 정리 보완](../research/2026-10-24-094-search-plan-reliability.md), [계획서 동작](../travel-plan.md), `travel_plan.mutate`와 `RunManager`.
- 기술별 이유: JSON은 실행별 구조화 계획을 저장한 실제 형식이다. 계획서를 열 때 새 생성을 요구하지 않고 저장 데이터를 사용한다. Human-in-the-loop는 구현된 사용자 편집·선택 확정의 역할을 가리킨다.
- 대안과 대가: 버튼을 누를 때 답변을 새로 생성하거나 모델이 선택을 자동 확정하는 방식보다, 저장 초안과 사용자 결정을 나눴다. 내용 변경 시 확정 상태도 함께 관리한다.
- 공고 연결: 공고1의 실제 서비스 기능 실행·고객 문제 해결, 공고2의 사용자 경험·신뢰·실행 권한 설계.

## 근거를 본문으로 바꾸는 규칙

각 파트의 작성용 카드는 `문제 → 검토한 대안 → 선택 이유 → 실제 근거 → 공고 요구 → 보여줄 그림`을 갖춘다. 당시 선택 근거가 없는 항목은 추가 확인 또는 기능 설명으로 표현을 조정한다. 사후에 그럴듯한 이유를 당시 의사결정으로 바꾸지 않는다.

제출 본문에는 카드 전체를 복사하지 않는다. 기술명이 있는 제목, 핵심 구조, 짧은 선택 이유와 이해를 돕는 시각 자료로 압축한다. 위의 내부 확인 문구·미측정 항목을 자동으로 본문에 붙이지 않는다.
